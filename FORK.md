# This fork

This repository is a fork of [anomalyco/opencode](https://github.com/anomalyco/opencode) (`upstream`). It adds:

- **`/merge`**: drive Claude Code (and future adapters) from an OpenCode session.
- **The iphi theme**: the default look.
- **An operator console**: `/operator/*` pages and the left sidebar, plus Settings → Adapters and Settings → Organization → Namespaces (prompt profiles per organization).
- **A Docker-only dev stack**: in `docker/dev`.

The fork is built so that new upstream releases merge with as few conflicts as possible.

## How fork code is laid out

Fork code lives in **fork-only paths**. Upstream never touches them, so they never conflict.

## Rules for new fork work

1. **Put new code in a fork-only path.**
2. **Register through the existing aggregators instead of editing upstream again:**
   - Routes: add a per-project group to `OperatorApi` in `packages/opencode/src/operator/http/api.ts`, or a server-wide one to `OperatorRootApi` (`http/groups/overview.ts`, as `http/groups/folders.ts` is), and its handler to `http/handlers.ts`. Add its HTTP scenarios to `test/server/httpapi-exercise/operator.ts`. A `GET` route must not have the same path as a web page (`/operator/memory` is a page, so its data is `/operator/memory/overview`): where the app and the API share an origin, the page would load as JSON.
   - Services the routes need: add them to `packages/opencode/src/operator/nodes.ts`.
   - Top-level config keys: add them to `fields` in `packages/core/src/v1/config/fork.ts`; agent keys to `agentFields` there.
   - Built-in plugins: add them to `operatorPlugins` in `packages/opencode/src/operator/plugins.ts`.
   - Web pages: add them to `packages/app/src/operator/pages.ts` and their component to `routes.tsx`. The routes, sidebar and command palette all read the list.
   - Things on the session page: mount them from the fork-owned sidebar (as `inspector/` does through the titlebar's right-hand slot), not from session page files.
   - UI strings: add them to `packages/app/src/operator/i18n/en.ts`, **not** the 62 upstream locale files. Every locale falls back to these English strings.
3. **Prefer events and hooks to edits.** Subscribe to bus events or use plugin hooks rather than changing upstream logic.
4. **Keep unavoidable upstream edits small and list them below.** For example: a new agent config key must go in `KNOWN_KEYS`, or it is sent to the model provider.
5. **Don't move fork helpers into upstream modules that tests mock.** Some upstream tests mock whole modules, for example `@opencode-ai/session-ui/message-part`. A fork export in such a module disappears under the mock.

## Merging an upstream release

```sh
script/fork/upstream-merge.sh            # fetch upstream/dev and merge it into the current branch
script/fork/upstream-merge.sh --check    # only run the checks (after resolving conflicts)
```

The script works in four stages:

1. It adds the `upstream` remote if it is missing, fetches it, and merges `upstream/dev`. It stops if there are conflicts.
2. **Conflicts:** resolve the files, using the table above, and commit. Then run `--check`.
3. **Checks:** in Docker with limits (see `docker/dev/README.md`), it:
   - regenerates the SDKs and migrations;
   - typechecks the touched packages;
   - runs the merge and operator tests, the HttpApi coverage gate, and the app unit tests.
4. It lists upstream files the fork now edits that are missing from the table above.

**Prompt texts.** Prompt profiles (the Prompt Profile page) show every text OpenCode adds to a prompt as a built-in layer, and the built-in **OpenCode** profile must keep giving upstream's system prompt byte for byte (the helper profiles **Title**, **Summary** and **Compaction** do the same for those agents, and **Agent generator** for the agent generator's call). So new upstream texts must become layers. After a merge, check `session/system.ts`, `session/prompt/*.txt`, `session/reminders.ts`, and the system parts that `session/prompt.ts` and `session/llm/request.ts` pass to the `experimental.chat.system.transform` hook:

- a new base prompt or model family is a **Base Model Group** layer (type Agent identity): add it to `BUILTINS` in `packages/opencode/src/operator/prompt-text.ts` (and to `baseFor` if it has its own model rule), with its description as `operator.prompts.id.<id>` in `packages/app/src/operator/i18n/en.ts`;
- a new notice for structured answers is an **Output format** layer (`notice.*` in `BUILTINS`);
- a new reminder or notice (added to the conversation, not the system prompt) is a **Message text** (type Platform/system constraints; `reminder.*`, `notice.*` in `BUILTINS`); reminders are matched back to their text by `rewriteReminder`;
- a new built-in agent with its own prompt (like `explore`'s `agent/prompt/explore.txt`) is not a layer (the agent-prompt slots resolve it per agent): add it to `AGENT_PROMPTS` in `prompt-text.ts` with its file, so the agent page names where it comes from;
- a new hidden agent with its own prompt (like `title`, `summary`, `compaction` in `agent/agent.ts`), or a one-call prompt (like `agent/generate.txt`), is a **Helper** layer: add `helper.<name>` to `BUILTINS` (it gets a helper layer and a helper profile), and its name to `HELPER_DEFAULTS` in `profile.ts`;
- a new section OpenCode writes for every request is a **Dynamic** layer (type Dynamic): add a field to `SystemParts` (`packages/plugin/src/index.ts`, `session/llm/request.ts`, `session/prompt.ts`), a `generated.<name>` layer to `BUILTIN_LAYERS` and its resolution to `resolve` in `packages/opencode/src/operator/profile.ts`, and put it in the OpenCode profile's Dynamic slot where upstream sends it. Where it goes in the Spec profile is the user's choice: ask first, as for any change to the built-in groups and profiles.

Every entry in `BUILTINS` and `AGENT_PROMPTS` names the upstream file its text comes from (`file`; a test checks each exists), and `OperatorPromptText.baseRule` restates `SystemPrompt.provider`'s rules (a test checks they agree): update both when upstream moves a prompt file or changes the model rules. The agent page declares the texts OpenCode adds that are not layers (`pages/prompt-exceptions.ts`, with their files): keep that list in line after a merge. `operator/models.ts` names where an agent's model comes from by reusing `Provider.defaultModel` and `getSmallModel` (`provider/provider.ts`) and reading what they read (config `model`/`small_model`, `model.json`): check it when those change.

The Prompt Profile page describes where each per-request layer's text comes from (**Text source**, `operator.layer.source.*` in `packages/app/src/operator/i18n/en.ts`) and what it depends on (`DEPENDS_ON` in `pages/profile-model.ts`); Generate sample names the actual source (`originOf` in `operator/prompts.ts`, `promptOrigin` in `operator/agents.ts`). After a merge, check them against `SystemPrompt.provider` and `environment`/`skills`/`mcp` (`session/system.ts`), `session/instruction.ts`, the skill folders in `skill/index.ts`, and the agent and config loading in `agent/agent.ts` and `config/config.ts`. The Capabilities page marks OpenCode's own commands by name (`BUILTIN_COMMANDS` in `pages/capabilities.tsx`): keep it in line with `Default` in `command/index.ts`.

A helper agent's prompt is its helper layer, so upstream's `agent.<name>.prompt` config key no longer changes `title`, `summary` or `compaction`; an editable copy of the helper layer in a helper profile does.

The fork has two helpers of its own, `purpose-generator` (drafts org and project purposes, `POST /operator/prompt/purpose`) and `dynamic-generator` (writes your Dynamic layers), plus `agent-generator`, the name upstream's agent generator call goes by. They are not registered agents (registering them through the plugin `config` hook would put them in `GET /config`); their one model call is `operator/generate.ts`, made like upstream's project-copy name call (`LLM.stream` carrying the agent; the small model), and the prompt plugin gives it the agent's helper profile by name. Your Dynamic layers hold a prompt; `operator/helper-texts.ts` writes their text once per root session (cached under the data folder's `operator/dynamic/`). Plugins cannot reach Effect services, so that service registers itself in `operator/registry.ts` when the server builds it, and the prompt plugin calls it with the request's instance (`InstanceRef`, read from the request fiber before anything is awaited).

System text that a caller passes without a label arrives in `SystemParts.extra` and is sent, unlabelled, at the end of the system message; give it a label. `test/operator/prompts-e2e.test.ts` fails when the OpenCode profile no longer reproduces upstream's prompt, a tool description or a reminder, or when the agent page's preview no longer matches what is sent.

**Projects and the session guard.** Every session, and the agents it runs, belongs to one project: a git repository, or a folder outside git registered as a project (its subfolders belong to it too); see `packages/opencode/src/operator/projects.ts`. A fork-owned global middleware (`operator/http/session-guard.ts`, merged into `operatorRootRoutes`) runs before upstream's routes and refuses `POST /session`, `POST /session/:id/fork` and `POST /api/session` in a folder that is not part of a project, with an `OperatorNotAProjectError` (409); upstream's routes are untouched. Upstream's test suite starts sessions in plain temporary folders, so the guard is off when `OPENCODE_TEST_HOME` is set (its test preload) and in the HttpApi exerciser; `OPENCODE_PROJECT_GUARD=on|off` overrides. Sessions that skip HTTP (`opencode github`, `debug agent`, the separate `packages/cli` server) are not guarded. If upstream adds a route that creates sessions, add it to the guard. A project can be copied into a new folder (`POST /operator/project-settings/register` with `from`): its `.opencode` folder and `opencode.json(c)` (`operator/project-copy.ts`), its prompt settings (`OperatorProfileStore.copyProject`; profiles are copied only into another namespace) and, when asked, its sessions. The sessions of a folder that is not a project can be moved into one or archived (`POST /operator/project-settings/folder/{move,archive}`). Both use `operator/project-sessions.ts`: a copied session is upstream's `Session.fork` run in the target's instance; upstream's move-session keeps a session in its project, so a move publishes `session.updated` with the target's project and folder instead. If upstream's session row or fork changes, check these.

Namespaces, their layers, groups and profiles, project links and agent settings are files under `~/.config/opencode/namespaces/` (`operator/profile-store.ts`); upstream never reads them. Built-in layers, groups and profiles belong to the OpenCode namespace; every other namespace gets its own copies when it is read (`adopt` in `profile-store.ts`, recorded in its `builtins.json`). So after a merge, a new built-in reaches other namespaces by itself, and a copied text whose built-in changed is flagged "OpenCode's text changed" (its `basedOn` fingerprint no longer matches), for the user to take the new text. Copied groups and profiles are not updated: when a merge changes the built-in OpenCode or Spec profile, say so in the release notes.

**Recorded model calls.** Every model call is recorded for the session views (`specs/docs/feedbacks/after iteration 4/session_view_redesign.md`): the fork's prompt plugin registers each call in `chat.headers` (`operator/calls.ts`, reached through `operator/registry.ts`) and adds `x-operator-call: <id>`; the tap in `provider/provider.ts` (`operator/provider-tap.ts`) removes that header, records the request at once and the response from a clone, both in the background. Bodies are stored split into content-hashed blobs (each message, the system text and the tools once; `operator/call-format.ts`), checked to rebuild byte for byte, under the data folder's `operator/calls/<sessionID>/` (`operator/call-store.ts`), and deleted with their session (`session.deleted`). Config `operatorRecordCalls: false` turns it off. If upstream's AI SDK version stops writing bodies with `JSON.stringify`, the byte check fails and calls are kept whole (marked); if upstream moves the fetch layer, move the tap. The native LLM runtime (`OPENCODE_EXPERIMENTAL_NATIVE_LLM`) does not go through `timeoutFetch`, so its calls are not recorded.

**Tool prompt and permissions.** The agent's Tool Prompt tab (`operator/tool-prompt.ts`) builds the tools list a request sends with the functions a request uses (`ToolRegistry.tools`, `ToolJsonSchema.fromTool`, `ProviderTransform.schema`, `Permission.disabled`), and **mirrors steps upstream does not export**: the MCP tools and MCP resource tools (`session/tools.ts`), `resolveTools`, `strict: false`, Copilot's `_noop` and the sort (`session/llm/request.ts`), `invalid` never offered (`session/llm.ts`), and the model and flag reasons a tool is not offered (`tool/registry.ts`). `test/operator/tool-prompt.test.ts` compares it with real requests; after a merge, if it fails, bring the mirror in line. The permission editor (`operator/permission-rules.ts`) labels an agent's rules by matching the parts `agent/agent.ts` puts together (defaults, the agent's definition, config `permission` and legacy `tools`, the agent's own rules, the truncation folder) and the rules `tool/task.ts` and `agent/subagent-permissions.ts` give a subagent session; `FORMS` there says which pattern each permission is asked with (from each tool's `ctx.ask` call). Check both when those files change. Session rule origins are kept in `<data>/operator/session-permissions.json`; "Always" answers and client tool switches reach it through `operator/permission-hook.ts` (the two fork lines in `permission/index.ts` and `session/prompt.ts`).

**Upstream's worktree race.** The HttpApi gate (`bun run test:httpapi`) can hang in its effect mode, on upstream's `worktree.create` scenario (`test/server/httpapi-exercise/index.ts`): the server answers and keeps loading the new worktree's instance in the background (`createFromInfo` forks `boot` in `src/worktree/index.ts`); the scenario's cleanup then disposes all instances, which waits for that load (`disposeAll` in `src/project/instance-store.ts`); the load stalls at its start ("bootstrapping" and no config load in the log), and cleanup runs after the scenario's 30-second timeout and cannot be interrupted, so the run waits forever. It depends on timing (more likely on a busy machine) and is upstream's: it happens before any operator route runs. `script/fork/upstream-merge.sh --check` gives the gate 10 minutes (a run takes about 4) and runs it once more if it times out. If upstream fixes the race, drop the retry.

**Selectable text.** Upstream makes the new layout's content area unselectable (`select-none` in `pages/layout-new.tsx`), and its settings panel too. The fork turns selection back on for text everywhere with one unlayered stylesheet, `packages/app/src/operator/ui/selectable.css` (loaded with the operator sidebar), and keeps controls unselectable; no upstream file changes. If upstream adds selection rules more specific than it, or new kinds of controls, check them against it.

**Trash.** Every delete in the operator pages moves the item to Trash (`operator/trash-files.ts` on disk, `operator/trash.ts` and `operator/trash-items.ts` as services; routes under `/operator/trash`): files and folders are moved into the data folder's `operator/trash/<id>/` (a project's whole folder, with its prompt settings kept and its sessions archived), and config entries (MCP servers, agents and commands defined in config) are removed and kept, to be written back on restore. Deleting from Trash is for good (sessions with it). The folder OpenCode runs from, the home folder and folders holding OpenCode's data cannot be moved. Upstream has no unarchive (its session projector leaves the archive time when an update has none), so restoring clears it in the session row and then publishes the update; if upstream adds unarchive, use it. The Trash page is `/operator/deleted`, since `/operator/trash` is an API route.

```sh
docker compose -f docker/dev/compose.yaml run --rm e2e npx playwright test e2e/operator e2e/regression e2e/smoke
```
