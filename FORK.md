# This fork

This repository is a fork of [anomalyco/opencode](https://github.com/anomalyco/opencode) (`upstream`). It adds:

- **`/merge`**: drive Claude Code (and future adapters) from an OpenCode session.
- **The iphi theme**: the default look.
- **An operator console**: `/operator/*` pages and the left sidebar, plus Settings → Adapters and Settings → Organization → Namespaces (prompt profiles per organization).
- **A Docker-only dev stack**: in `docker/dev`. It mounts your home folder into the server at the same path, the production model (`compose.isolated.yaml` keeps the server's data in volumes instead), and serves the app and the API on one origin, 4444 (`packages/app/vite.dev-stack.config.ts` forwards the API to the server).

The fork is built so that new upstream releases merge with as few conflicts as possible.

## Rules for new fork work

1. **Put new code in a fork-only path.**
2. **Register through the existing aggregators instead of editing upstream again:**
   - Routes: add a per-project group to `OperatorApi` in `packages/opencode/src/operator/http/api.ts`, or a server-wide one to `OperatorRootApi` (`http/groups/overview.ts`, as `http/groups/folders.ts` is), and its handler to `http/handlers.ts`. Add its HTTP scenarios to `test/server/httpapi-exercise/operator.ts`. A `GET` route must not have the same path as a web page (`/operator/memory` is a page, so its data is `/operator/memory/overview`): where the app and the API share an origin, the page would load as JSON.
   - Services the routes need: add them to `packages/opencode/src/operator/nodes.ts`.
   - Top-level config keys: add them to `fields` in `packages/core/src/v1/config/fork.ts`; agent keys to `agentFields` there.
   - Built-in plugins: add them to `operatorPlugins` in `packages/opencode/src/operator/plugins.ts`.
   - Web pages: add them to `packages/app/src/operator/pages.ts` and their component to `routes.tsx`. The routes, sidebar and command palette all read the list.
   - Things on the session page: mount them from the fork-owned sidebar (as `inspector/` does through the titlebar's right-hand slot), not from session page files.
   - UI strings: add them to `packages/app/src/operator/i18n/en.ts`, **not** the 62 upstream locale files. Every locale falls back to these English strings.
3. **Prefer events and hooks to edits.** Subscribe to bus events or use plugin hooks rather than changing upstream logic.
4. **Keep unavoidable upstream edits small and list them below.** For example: a new agent config key must go in `KNOWN_KEYS`, or it is sent to the model provider.
5. **Don't move fork helpers into upstream modules that tests mock.** Some upstream tests mock whole modules, for example `@opencode-ai/session-ui/message-part`. A fork export in such a module disappears under the mock.

## Merging an upstream release

```sh
script/fork/upstream-merge.sh            # fetch upstream/dev and merge it into the current branch
script/fork/upstream-merge.sh --check    # only run the checks (after resolving conflicts)
```

The script works in four stages:

1. It adds the `upstream` remote if it is missing, fetches it, and merges `upstream/dev`. It stops if there are conflicts.
2. **Conflicts:** resolve the files, using the table above, and commit. Then run `--check`.
3. **Checks:** in Docker with limits (see `docker/dev/README.md`), it:
   - regenerates the SDKs and migrations;
   - typechecks the touched packages;
   - runs the merge and operator tests, the HttpApi coverage gate, and the app unit tests.
4. It lists upstream files the fork now edits that are missing from the table above.

**Prompt texts.** Prompt profiles (the Prompt Profile page) show every text OpenCode adds to a prompt as a built-in layer, and the built-in **OpenCode** profile must keep giving upstream's system prompt byte for byte (the helper profiles **Title**, **Summary** and **Compaction** do the same for those agents, and **Agent generator** for the agent generator's call). So new upstream texts must become layers. After a merge, check `session/system.ts`, `session/prompt/*.txt`, `session/reminders.ts`, and the system parts that `session/prompt.ts` and `session/llm/request.ts` pass to the `experimental.chat.system.transform` hook:

- a new base prompt or model family is a **Base Model Group** layer (type Agent identity): add it to `BUILTINS` in `packages/opencode/src/operator/prompt-text.ts` (and to `baseFor` if it has its own model rule), with its description as `operator.prompts.id.<id>` in `packages/app/src/operator/i18n/en.ts`;
- a new notice for structured answers is an **Output format** layer (`notice.*` in `BUILTINS`);
- a new reminder or notice (added to the conversation, not the system prompt) is a **Message text** (type Platform/system constraints; `reminder.*`, `notice.*` in `BUILTINS`); reminders are matched back to their text by `rewriteReminder`;
- a new built-in agent with its own prompt (like `explore`'s `agent/prompt/explore.txt`) is not a layer (the agent-prompt slots resolve it per agent): add it to `AGENT_PROMPTS` in `prompt-text.ts` with its file, so the agent page names where it comes from;
- a new hidden agent with its own prompt (like `title`, `summary`, `compaction` in `agent/agent.ts`), or a one-call prompt (like `agent/generate.txt`), is a **Helper** layer: add `helper.<name>` to `BUILTINS` (it gets a helper layer and a helper profile), and its name to `HELPER_DEFAULTS` in `profile.ts`;
- a new section OpenCode writes for every request is a **Dynamic** layer (type Dynamic): add a field to `SystemParts` (`packages/plugin/src/index.ts`, `session/llm/request.ts`, `session/prompt.ts`), a `generated.<name>` layer to `BUILTIN_LAYERS` and its resolution to `resolve` in `packages/opencode/src/operator/profile.ts`, and put it in the OpenCode profile's Dynamic slot where upstream sends it. Where it goes in the Spec profile is the user's choice: ask first, as for any change to the built-in groups and profiles.

Every entry in `BUILTINS` and `AGENT_PROMPTS` names the upstream file its text comes from (`file`; a test checks each exists), and `OperatorPromptText.baseRule` restates `SystemPrompt.provider`'s rules (a test checks they agree): update both when upstream moves a prompt file or changes the model rules. The agent page declares the texts OpenCode adds that are not layers (`pages/prompt-exceptions.ts`, with their files): keep that list in line after a merge. `operator/models.ts` names where an agent's model comes from by reusing `Provider.defaultModel` and `getSmallModel` (`provider/provider.ts`) and reading what they read (config `model`/`small_model`, `model.json`): check it when those change.

The Prompt Profile page describes where each per-request layer's text comes from (**Text source**, `operator.layer.source.*` in `packages/app/src/operator/i18n/en.ts`) and what it depends on (`DEPENDS_ON` in `pages/profile-model.ts`); Generate sample names the actual source (`originOf` in `operator/prompts.ts`, `promptOrigin` in `operator/agents.ts`). After a merge, check them against `SystemPrompt.provider` and `environment`/`skills`/`mcp` (`session/system.ts`), `session/instruction.ts`, the skill folders in `skill/index.ts`, and the agent and config loading in `agent/agent.ts` and `config/config.ts`. The Capabilities page marks OpenCode's own commands by name (`BUILTIN_COMMANDS` in `pages/capabilities.tsx`): keep it in line with `Default` in `command/index.ts`. Its Skills tab explains, in words, how skills are found and which agents get them ("How skills reach an agent", `operator.skillsNote.text`; the Dynamic Skills layer's Text source says the same in short). `specs/docs/feedbacks/capabilities/skill/skills_rules_note_spec.md` §4 names the code behind each rule: after a merge, re-check them against `skill/index.ts`, `config/paths.ts`, `effect/runtime-flags.ts`, `session/system.ts`, `tool/skill.ts`, `permission/index.ts` and `agent/agent.ts`, and update the note in the same commit.

A helper agent's prompt is its helper layer, so upstream's `agent.<name>.prompt` config key no longer changes `title`, `summary` or `compaction`; an editable copy of the helper layer in a helper profile does.

The fork has two helpers of its own, `purpose-generator` (drafts org and project purposes, `POST /operator/prompt/purpose`) and `dynamic-generator` (writes your Dynamic layers), plus `agent-generator`, the name upstream's agent generator call goes by. They are not registered agents (registering them through the plugin `config` hook would put them in `GET /config`); their one model call is `operator/generate.ts`, made like upstream's project-copy name call (`LLM.stream` carrying the agent; the small model), and the prompt plugin gives it the agent's helper profile by name. Your Dynamic layers hold a prompt; `operator/helper-texts.ts` writes their text once per root session (cached under the data folder's `operator/dynamic/`). Plugins cannot reach Effect services, so that service registers itself in `operator/registry.ts` when the server builds it, and the prompt plugin calls it with the request's instance (`InstanceRef`, read from the request fiber before anything is awaited).

System text that a caller passes without a label arrives in `SystemParts.extra` and is sent, unlabelled, at the end of the system message; give it a label. `test/operator/prompts-e2e.test.ts` fails when the OpenCode profile no longer reproduces upstream's prompt, a tool description or a reminder, or when the agent page's preview no longer matches what is sent.

**Dynamic layers resolve through one pipeline** (`specs/docs/feedbacks/prompt/dynamic_layer_resolution_spec.md`; `operator/resolver.ts`, `operator/resolver-builtins.ts`, `operator/dynamic-layers.ts`, `operator/resolutions.ts`). Sources → Read → Filter → Score → Select → Render → Trace: a layer's resolver (data: sources, filters, score rules, a policy of one, top N or all per sub-group within a budget, a template) and the candidates its sources gave produce its text and a trace of every candidate (read, filtered, scored, selected or why not). OpenCode's Dynamic layers are resolvers in `resolver-builtins.ts` that reproduce upstream's texts: the base prompt by model (the family the model's rule chose; a profile's copy, then the namespace's version, then OpenCode's), Agent prompt, Agent prompt else base prompt, Environment, References, Instructions (per group the first name of AGENTS.md, CLAUDE.md, CONTEXT.md with all its files, then config's files and URLs, each path once), MCP instructions and Skills. `dynamic-layers.ts` reads their sources for each request as `session/system.ts` and `session/instruction.ts` do (URLs are not fetched again: the texts upstream fetched for the request are used); the prompt plugin reaches it through `OperatorRegistry.dynamicLayers`, the agent page's preview directly. Each request compares the pipeline's text of OpenCode's layers with the one upstream wrote for it (`systemParts`, `parts.base`): when they differ, upstream's text is sent and the section says `parity: differs`. `test/operator/prompts-e2e.test.ts` then fails, so **after a merge that changes how upstream writes one of these texts, port the change into `resolver-builtins.ts` / `dynamic-layers.ts`**. Sections carry their resolution (`resolution`; for Agent prompt, else base prompt, the base prompt's as `inner`), shown under each Dynamic section on the agent page and in a layer's sample (`app/src/operator/ui/resolution.tsx`). Each recorded call keeps its request's resolutions: the prompt plugin hands them from `experimental.chat.system.transform` to `chat.headers` (the same fiber) and on to `OperatorRegistry.calls.begin`; the provider tap stores them once as a blob (`Call.resolutions`), and the call's detail returns them for the Transcript. `resolutions.ts` keeps a session's resolutions of layers whose sources are slow, in `<data>/operator/resolutions/<session>.json`, reused while their signature is the same and gone with the session. Resolving the five per-request layers costs about 6 ms per request once warm. **Layers with rules of their own** (§6): your Dynamic layers and a namespace's copies of the five per-request layers keep a `resolver:` in their layer file's frontmatter (`profile-store.ts`; rules equal to the default, the helper's or OpenCode's, are not written, so the layer follows them). `dynamic-layers.ts` reads their sources one by one (`readSource`: files and globs, `~/.config/opencode/` meaning the global config folder; config values, `instructions` and `references`; URLs, fetched once per session; `environment`; the `skills` and `mcp` registries; the agent's prompt or description; texts; a `helper` source written by `OperatorHelperTexts` from the layer's prompt). Your Dynamic layers written by a helper are layers with one helper source (`HELPER_RESOLVER`), the same text as before. OpenCode's rules read this way give OpenCode's texts (`test/operator/prompts-e2e.test.ts`), so Edit a copy of a per-request layer makes one of your Dynamic layers with the same rules. The layer overlay shows the rules (`app/src/operator/pages/layer-rules.tsx`), edits them in place, and Test resolve is the layer sample (`GET /operator/prompt/sample`) with draft rules (`resolver`), a model and a session. **A helper judge** (§2.3, off by default; the rules' `judge`: a helper of the namespace that only reads, its weight and instructions): `dynamic-layers.ts` asks it (`helper-texts.ts` `judge`, a recorded run started by the layer) about the candidates the filters kept, and its 0–1 score times the weight is a score part (`resolver.ts`, trace `judge`). Its scores are kept with the session's root (`<data>/operator/dynamic/<session>.json`, key `judge:<layer>`) and asked again only when the candidates or the judge's settings change, never per turn; a failure is kept the same way; the agent page's preview doesn't ask it. A helper that judges a layer, like one that writes it, may declare only read actions and isn't deleted while it does.

**Short-term memory** (`specs/docs/feedbacks/memory/memory_spec.md`). Each level has a `.memory` folder (`operator/memory-folders.ts`): the namespace's in its folder (Global's in the global config folder), the project's at its root, an agent's in its home or, without one, in `<project>/.memory/agents/<name>/`. New agents from the agent form get the home `agents/<name>/`. `.memory` folders are kept out of git by a line in the repository's `.git/info/exclude` (marked as OpenCode's; a linked worktree's goes in its main repository's), never in `.gitignore`; Memory → Settings (`GET/PUT /operator/memory/settings`, kept in `<config>/namespaces/memory.json` with the prompts' index limits) can commit them, by default or per project, and then only the marked line is taken out. The format (`operator/memory-format.ts`: `MEMORY.md` lines `- [title](file.md) — description`, a slug per memory, frontmatter files) is read and written by one module (`operator/memory-store.ts`: atomic writes, one lock per folder, lines that are not entries kept). The **`memory` tool** (`operator/memory-tool.ts`, a tool of the fork's prompt plugin) lists, reads, saves, updates and forgets (to Trash); every action asks the `memory` permission as `READ|WRITE|FORGET(<level>/<file>)` with the memory's title, description and a diff for the reply card; a subagent's session runs incognito unless its agent is retentive (namespace and project memory only, never writing; see Agent types below). Its context comes from `operator/memory-service.ts` through `OperatorRegistry.memory`. The tool is an **opt-in tool** (`OperatorPermissionEffective.declareOptIn`): the effective permission set says which are offered (`offered`, from the `handlers.offered` hook, which `permission-live.ts` calls); it is offered in every namespace but OpenCode's, and there only when the agent's profile holds a memory layer or a `memory` allow is set below Global, so OpenCode's tool list stays upstream's. The `memory` permission's defaults (`operator/memory-defaults.ts`) are written once at start: into the global config, and each other namespace's config at its level (also when a namespace is created); a flag in the namespaces' `settings.json` keeps lines the user deleted from coming back (off in test runs unless `OPENCODE_MEMORY_DEFAULTS=on`). **The memory layers** (`generated.memory-namespace`, `-project`, `-agent`) show each level's index on the Dynamic layer pipeline (`dynamic-layers.ts` `memoryLayers`, `resolver-builtins.ts` `memoryResolver`): newest first, cut at the limits from Memory → Settings with a "…N more memories" line (the resolver's overflow counts a top N's cut too), nothing for an empty index; the READ decision of the session's rules shows the index (allow), one line saying it is there (ask) or nothing (deny); an incognito session has no agent memory. An index is read again only when its `MEMORY.md` changes. The built-in text `notice.memory` (copyable) goes once before the first memory block. The built-in Spec profile holds the layers last in Dynamic; OpenCode's OpenCode profile does not (it stays upstream's). Every other namespace's copies of the OpenCode and Spec profiles get them when the namespace first takes them (`profile-store.ts` `addMemoryLayers`). **The Memory page** (`app/src/operator/pages/memory.tsx`, `memory-levels.tsx`, `memory-files.tsx`; `operator/memory-page.ts`, routes `/operator/memory/levels|entry|index`) is scoped by the namespace picked at its top: the Memory tab shows the namespace's memory, then a project's (picked just above it), then an agent's of that project (picked just above it), each with its own New memory and Edit MEMORY.md; a memory opens in an overlay to read, edit or delete (to Trash), all with `memory-store.ts`. Files lists the namespace's projects' prompt files in one table (instruction files only for OpenCode's and Global's projects), Summaries their compaction summaries, and Settings the namespace's memory settings (commit choice and index limits per namespace, OpenCode's until it sets its own, kept in `<config>/namespaces/memory.json`; a project's own commit choice is also on its record) and the server's database. **Instruction files** (`AGENTS.md`, `CLAUDE.md`, `CONTEXT.md`, config `instructions`) load only for those projects: upstream's `session/instruction.ts` asks `operator/instruction-scope.ts` in `system()` and `resolve()`, the pipeline's Instructions layer adds nothing elsewhere (so its parity stays "same"), and other namespaces' copies of OpenCode's profiles leave the Instructions layer out. **Each tool's permission pattern** (`operator/tool-patterns.ts`, routes `/operator/capability/tool-patterns` and `/tool-pattern`; memory_spec.md §9): the permission its rules use, its verbs, what the pattern is matched against, examples and the rules that apply by default. OpenCode's tools (and the fork's `memory`) are a table filled in from their `ctx.ask` calls, so **when upstream changes how a tool asks, update `BUILTINS` there**; MCP tools always ask with `*`; a custom tool's is written by the user (asked for when it is created on the Capabilities page) in `<config>/namespaces/tool-patterns.json`. It shows on the tool's card and as help under the permission editor's add-rule row.

**Projects and the session guard.** Every session, and the agents it runs, belongs to one project: a folder the console recorded as a project in `projects.json` (a git repository or a folder outside git; its subfolders belong to it too); see `packages/opencode/src/operator/projects.ts`. A folder OpenCode only knows from its database (a repository a client opened, the server's own folder) is not a project, a git repository included (`specs/docs/issues/002`, the user's decision, 2026-10-12): the console's lists show only records, and a repository becomes a project through the Projects page (registering a folder inside one is refused). Each record has a **short id** (`operator/project-ids.ts`: 5 lowercase base-32 characters, unique on the server), made when the record is, kept through moves and renames (they rewrite keys, not values); at the first start with records, the projects the console listed until then (git projects in the database not in Trash, and every project with settings) became records once (`projectRecords` in `<config>/namespaces/settings.json`). The pickers label projects "name · id", show a project's or namespace's folder on hover, and show the chosen ones' ids beside them (`ui/id-chip.tsx`); a `?dir=` link to a folder that isn't a project says so and offers to make it one. Trash takes only records. A fork-owned global middleware (`operator/http/session-guard.ts`, merged into `operatorRootRoutes`) runs before upstream's routes and refuses `POST /session`, `POST /session/:id/fork` and `POST /api/session` in a folder that is not part of a project, with an `OperatorNotAProjectError` (409); upstream's routes are untouched. Upstream's test suite starts sessions in plain temporary folders, so the guard is off when `OPENCODE_TEST_HOME` is set (its test preload) and in the HttpApi exerciser; `OPENCODE_PROJECT_GUARD=on|off` overrides. Sessions that skip HTTP (`opencode github`, `debug agent`, the separate `packages/cli` server) are not guarded. If upstream adds a route that creates sessions, add it to the guard. A project can be copied into a new folder (`POST /operator/project-settings/register` with `from`): its `.opencode` folder and `opencode.json(c)` (`operator/project-copy.ts`), its prompt settings (`OperatorProfileStore.copyProject`; profiles are copied only into another namespace) and, when asked, its sessions. The sessions of a folder that is not a project can be moved into one or archived (`POST /operator/project-settings/folder/{move,archive}`). Both use `operator/project-sessions.ts`: a copied session is upstream's `Session.fork` run in the target's instance; upstream's move-session keeps a session in its project, so a move publishes `session.updated` with the target's project and folder instead. If upstream's session row or fork changes, check these.

**The Config reference** (`specs/docs/issues/003`): every Config page (a project's, a namespace's, Global's) ends with a reference of every option the config accepts (`app/src/operator/pages/config-reference.tsx`), served by `GET /operator/config/reference` (`operator/config-reference.ts`). It is built from upstream's config schema (`ConfigV1.Info`, the fork's keys from `core/src/v1/config/fork.ts` included), so options upstream adds appear on their own. Descriptions are the schema's; an option without one gets the fork's text from `operator/config-texts.ts`, keyed by path (a built-in agent's or a legacy mode's option reads as `agent.<name>.…`, the deprecated `reference.*` as `references.*`). `test/operator/config-reference.test.ts` fails when an option has neither: **after a merge that adds config options without descriptions, add their texts to `config-texts.ts`**, never to upstream's schema files. A new map key's placeholder (`<id>`, `<name>`) is `KEY_NAMES` there, a new section's documentation link `DOCS`.

**Project records, members, agent sessions and queues** (`specs/docs/feedbacks/project-agent specification.md`). A project's record (description, status, manager, members, groups) is in `~/.config/opencode/namespaces/project-records.json` (`operator/project-records.ts`); its goal is the project's linked Purpose layer, not a field. When a project names members, the session guard also refuses a request that would run an agent that is not one, with `OperatorNotAMemberError` (403): `POST /session` with an `agent`, and `POST /session/:id/{message,prompt_async,command}` naming an agent, checked against the project of the new session's folder or the session's own folder. The helpers `title`, `summary` and `compaction` are exempt. If upstream adds a route that runs an agent, add it to `agentOf()` in `session-guard.ts`. An agent's main session per project and its default queue target are in `<data>/operator/agent-sessions.json` (`operator/agent-sessions.ts`); its active session is worked out from upstream's session table (the latest `time_updated` in the project, same `agent`, no parent, not archived), so check `inProject` and that query if the session row changes. Agents' input queues are a SQLite file of the fork's own, `<data>/operator/queue.sqlite` (`operator/queue-store.ts`, behind a `Backend` interface so a broker can replace it). `operator/queue.ts` delivers them with upstream's `SessionPrompt.prompt`: a message waits until `SessionStatus` says its session is idle (and until the fork's own delivery into that session has returned), then starts its next turn; a steering message is prompted at once, which upstream's run state joins to the running loop. Delivery runs on `session.idle`/`session.status` events from the global bus and every 30 seconds. If upstream changes how a prompt into a busy session behaves (`SessionRunState.ensureRunning`), check steering. Routes: `/operator/project-records`, `/operator/agent/:name/{session-state,main,target,queue}`, `/operator/main-session`, `/operator/queue[/:id]`.

Namespaces, their layers, groups and profiles, project links and agent settings are files under `~/.config/opencode/namespaces/` (`operator/profile-store.ts`); upstream never reads them. A namespace's **folder** is `<working directory>/<id>` (see Layout below; a record names one only while the namespace isn't in place; new projects are made in it; its `.opencode` is the namespace's layer of capabilities, between the global config and the project's, see below) and its **default project** (the chosen one while it is still in the namespace, else its first, the earliest added); the working directory is set once on first start from `OPENCODE_OPERATOR_WORKING_DIR` (else the parent of the folder OpenCode's record names) and OpenCode's default project from `OPENCODE_OPERATOR_DEFAULT_PROJECT` (`docker/dev/compose.yaml`). Built-in layers, groups and profiles belong to the OpenCode namespace; every other namespace gets its own copies when it is read (`adopt` in `profile-store.ts`, recorded in its `builtins.json`). So after a merge, a new built-in reaches other namespaces by itself, and a copied text whose built-in changed is flagged "OpenCode's text changed" (its `basedOn` fingerprint no longer matches), for the user to take the new text. Copied groups and profiles are not updated: when a merge changes the built-in OpenCode or Spec profile, say so in the release notes.

**Scopes and words** (`specs/docs/feedbacks/namespace_project scopes/global_and_opencode_namespaces_spec.md` §3). "Global" is the namespace whose folder is `~/.config/opencode` (with `~/.opencode` as part of the Global base); "OpenCode" means only the namespace; "Built in" is OpenCode's own items; "Default" is a setting left unset; "Environment" is `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR` and `OPENCODE_CONFIG_CONTENT`, never Global and never written by the console. `operator/scopes.ts` `classify(path)` says where a file belongs (project, namespace, Global, environment or outside; the deepest folder wins, so a Global project's files are the project's). Every operator place that labels a file or picks a reload by path uses it (`models.ts`, `memory.ts`, `trash-items.ts`, and `OperatorReloadWhenIdle.wantFile`, used by the agent Permissions save and Allow for agent). The Config page's sources label `~/.opencode` as Global and the environment's files as Environment (`OperatorConfig.Source.kind` `env`).

**Layout** (`global_and_opencode_namespaces_spec.md` §4, §5, §9; `operator/layout.ts`). The **working directory** is in `~/.config/opencode/namespaces/settings.json` (`workingDir`; set in Settings → Namespaces while blank, `PUT /operator/layout/working-dir`; changing it once set comes with moving folders, and clearing it isn't offered). Every namespace except Global is at `<working directory>/<id>/`, its config in that folder's `.opencode/`; **Global** is a namespace too (record `namespaces/global/namespace.json`, created when the working directory is set), at `~/.config/opencode` with its config directly in it, always inheriting itself and never deleted. A **blank** working directory means Global and OpenCode are one namespace, "Global · OpenCode" (id `opencode`, `global` resolves to it, folder Global's), so a fresh install behaves as upstream. A namespace whose record still names another folder uses it and is flagged "Not in place" until it moves. **Membership is by location**: a project is in the namespace whose folder contains it (the deepest), else in OpenCode, flagged "Outside OpenCode's folder"; a `projects.json` assignment to another namespace stays until the project moves into its folder ("Not in place"). `namespace-scope.ts`, `profile-store.ts` (`ensure`, `settleLayout`), `config.ts`, `mcp-auth-scope.ts` and the permission levels read the layout from `OperatorLayout.snapshot()`; Global's permission lines are at the Global level, and its marks and locks reach every namespace that inherits it. `GET /operator/layout` lists each namespace's folder, target and config file and the flagged projects. Upstream never reads `settings.json`; nothing is moved or rewritten by this.

**A project's config is copy-on-write** (`global_and_opencode_namespaces_spec.md` §6, §7; `operator/project-config.ts`). A project uses its own config (the first of `.opencode/opencode.jsonc`, `.opencode/opencode.json`, `opencode.jsonc`, `opencode.json` in its folder) if it has one, else its namespace's; with its own, the namespace's config isn't merged (`OperatorNamespaceScope.configFiles`, and `OperatorConfig` mirrors it). Every operator write into a project's config goes through `OperatorConfig`'s project scope: without a config of its own, the project gets a full copy of its namespace's (`<project>/.opencode/opencode.jsonc`, comments kept, the change applied), recorded in `namespaces/project-config-copies.json` with the namespace file's hash ("changed since"). A project page never writes a namespace's or Global's config. Making the copy needs consent: the routes that can write project config (`PATCH /operator/config`, `PUT /operator/config/project`, capability actions, agent create/edit/delete, agent permissions, project permission levels, Allow for agent, Trash item removal) take `confirmCopy` and refuse without it (`OperatorProjectConfigCopyNeededError`, 409, `http/groups/project-config.ts`), which the app turns into the "Save as this project's own config?" question (`ui/project-config-copy.tsx`). Lines the namespace locks are never copied: they keep applying from the namespace's file (`permission-live.ts`), and the namespace's deletions are copied as the project's. "Use the namespace's config again" moves the project's own files to Trash (kind `config`, restorable with its copy record); a file git tracks is never removed. A namespace's and Global's config are edited only in Settings → Namespaces (`GET`/`PUT /operator/namespace/:id/config`), which also shows their effective settings and where each comes from, as a project's Config page does (`GET /operator/namespace/:id/config/effective`, §8): it loads an instance at the namespace's folder, and a namespace's own folder (Global's, for Global) is the namespace level, never a project with a config of its own (`OperatorNamespaceScope.layerOf` `atFolder`), so it gets Global's base (its capability keys only while the namespace inherits them), the namespace's config, then the environment, account and managed config. That instance stays loaded; the route compares the files it was loaded from with the files now and reloads it when they differ. Upstream's own config writers (the TUI's) are unchanged.

**Moving folders** (`global_and_opencode_namespaces_spec.md` §11; `operator/layout-move.ts`, `operator/path-rewrite.ts`). A project's namespace changes by moving its folder ("Move to namespace…", "Move into OpenCode's folder"); a namespace whose folder isn't `<working dir>/<id>` has "Move into place". `POST /operator/layout/plan` lists each folder from → to with its size, its sessions and what blocks it (the target exists, the move crosses file systems, linked git worktrees, running sessions, open terminals, protected folders: Global's folder, the working directory, OpenCode's own); `POST /operator/layout/move` moves the chosen ones one by one with a journal (`<data>/operator/moves/<id>.json`): the folder's instances stop, the folder is renamed, then every stored path is rewritten: the core database (`project.worktree`, `project.sandboxes`, `project_directory`, `workspace.directory`, `session_merge_binding.cwd`, in one transaction), sessions through `SessionV1.Event.Updated` (the session table is their projection), and the fork's stores listed in `OperatorPathRewrite.STORES` (written to a temporary file and swapped in, the old file kept until the move finishes), the queue, and the snapshot repositories (renamed to the new worktree's hash, `alternates` updated). Merged agents' own records of the folder's sessions follow it through their adapter's `relocator` (`merge/adapter/adapter.ts`), so `/merge` resumes those sessions in the new place instead of starting new ones: Claude Code finds a session only in `<CLAUDE_CONFIG_DIR or ~/.claude>/projects/<folder name>` of the folder it resumes in, so every such folder of a session that ran in the moved folder or below it is renamed to the new folder's name (which folder an entry belongs to is read from its transcripts' `cwd`; long names use Claude's own hash, `ClaudeSessions.folderName`), and each transcript line's `cwd` is rewritten (message contents keep the old paths: they are history); the plan shows how many follow, and blocks the item when that folder can't be written; the journal keeps what was done for a rollback. A project's prompt settings go with it (`setProject`, which copies what it uses into the new namespace). A failure rolls the item back; a journal a stopped server left is rolled back at the next start. Config files that name the old folder are listed in the report, not rewritten. **When upstream or the fork adds a store that keeps an absolute path, add it to `path-rewrite.ts`** (its test seeds every store). Upstream's own move-session and the TUI never move folders.

A helper runs as its own agent, `helper:<namespace>:<name>`: the one fork line in `agent/agent.ts` lets `Agent.get` find it (registered by each run, else built from the helper's file), and the prompt plugin gives it its helper profile. Without actions a run is one model call (`OperatorGenerate.call`, which also returns the cost); with actions it is a hidden session, a child of the calling session (so never in Chats, and its cost counts with the caller's), marked `metadata.operator.kind = "helper-run"`, with its step limit as the agent's `steps` and stopped at its time limit; the fork's session lists leave helper runs out. **What a run may do** is decided in `permission-live.ts` (`restrict`): allows only for declared tools (a line for every tool becomes one per declared tool), each declared tool allowed at the session level (more specific lines above still decide), asks turned into denies, and no memory of its own (locked denies on `agent/*`); `memory` is declared within the memory permission. So no run ever asks. Opt-in tools are offered by handlers in `OperatorPermissionEffective.offers` (memory-service.ts, helper-runs.ts). The purpose and Dynamic generators are the fork's: `helper-texts.ts` runs the role helper instead (a recorded run, started by the role). **A Dynamic layer of yours can name its writer** (`writer` in the layer's frontmatter; the layer editor's "Written by"): a helper of the namespace that only reads (`helper-files.ts` `LAYER_ACTIONS`), checked when the layer is saved and when the helper's actions change, and a helper can't be deleted while it writes a layer; without one, the namespace's Dynamic generator role, else OpenCode's. Its run is started by the layer (a child of the session, or archived for a preview). **Triggers** (§4.9; the user's choices of 2026-10-13): `triggers` in a helper's file start it on its own (`operator/helper-trigger-rules.ts` checks them; `operator/helper-triggers.ts`, a server-wide service, fires them). An agent's finished turn (`session.idle` or `session.status` idle on the global bus; helper runs and subagent sessions don't count) starts a run in the session's project, and a project the console records (`profile-store.ts` `projectCreated`, not the one-time adoption) one in the new project; schedules and untouched sessions run in the namespace's default project, as a recorded run started by the trigger. What each trigger fired, its skipped starts and last error are in `<data>/operator/helper-runs/triggers.json` (`GET …/triggers`). The scheduler's loop is off in test runs (`OPENCODE_HELPER_TRIGGERS=on|off`); tests call its `check`. If upstream renames `session.idle` or its payload, the turn trigger stops: check it.

**Capability scopes** (`specs/docs/feedbacks/namespace_project scopes/capability_scopes_spec.md`). A namespace's `<folder>/.opencode/` is laid out as a project's (opencode.jsonc, commands/, skills/, tools/, agents/, plugins/) and loads for every project of the namespace: OpenCode → Global → Namespace → Project, the nearer winning. `operator/namespace-scope.ts` finds a folder's project and namespace from the namespace store's files (it does not import the operator's services: `config/paths.ts` imports it) and gives `ConfigPaths.directories()` and `Config` the namespace folder; a namespace without a `.opencode` adds nothing, so the OpenCode namespace behaves as upstream until something is put in its folder. Like a project's `.opencode`, a loaded namespace folder gets OpenCode's `.gitignore` and its `@opencode-ai/plugin` install. It remembers which instance folders it served, so a project moving between namespaces, or a namespace's folder or inheritance changing, reloads exactly those (when idle). Disabling a command hides it whatever defines it (OpenCode's `init` and `review`, MCP prompts and skills listed as commands too), except the reserved `merge`. The same actions work at a namespace's scope (its folder's `.opencode` and `opencode.jsonc`), plus create, edit, delete and copy to another namespace; the Capabilities page has a Project / Namespace scope picker (`pages/capabilities.tsx`, `pages/capability-scope.tsx`). When an OpenCode release changes one of those texts, the copy shows "OpenCode's version changed" and **Take OpenCode's version** rewrites it; nothing changes by itself. After a merge, nothing needs doing for this: the fingerprints are compared with what OpenCode reports at run time. `OperatorConfig` has a third write scope, `namespace` (`WriteScope`; the agent and memory scopes stay global/project), used by the Config page's Namespace switch. After a merge, check that `directories()` still lists the global config folder first and that `Config` still merges the folder loop's JSON in the same place.

**Recorded model calls.** Every model call is recorded for the session views (`specs/docs/feedbacks/after iteration 4/session_view_redesign.md`): the fork's prompt plugin registers each call in `chat.headers` (`operator/calls.ts`, reached through `operator/registry.ts`) and adds `x-operator-call: <id>`; the tap in `provider/provider.ts` (`operator/provider-tap.ts`) removes that header, records the request at once and the response from a clone, both in the background. Config `operatorRecordCalls: false` turns it off. If upstream's AI SDK version stops writing bodies with `JSON.stringify`, the byte check fails and calls are kept whole (marked); if upstream moves the fetch layer, move the tap. The native LLM runtime (`OPENCODE_EXPERIMENTAL_NATIVE_LLM`) does not go through `timeoutFetch`, so its calls are not recorded. **Token accounting** (the Transcript, `specs/docs/feedbacks/transcript/transcript_view_spec.md`): `operator/call-accounting.ts` splits each recorded request into billed items (`operator/call-pieces.ts` reads each provider's message format) and attributes every billed token to one of them or to "Formatting and unattributed". It depends on upstream in five places, so check them after a merge. First, how usage is stored: `Session.getUsage` keeps input without the cache and output without reasoning, and `billed()` and `totalsOfStep()` mirror that. Second, the texts it recognizes: the in-memory reminders (from `prompt-text.ts`), `[Old tool result content cleared]`, and the truncation note in `tool/truncate.ts`. Third, the model prices from `Provider.getModel`. Fourth, the compaction marker: only an assistant message with `summary === true` is a compaction summary (upstream also sets `summary: {diffs}` on user messages). Fifth, retries: `operator/call-view.ts` groups the attempts of one step by the assistant message they share (the processor retries within the same message), falling back to the `retryOf` chain. Counts are stored per session in `<data>/operator/calls/<session>/accounting.jsonl`. Tokenizers are plug-ins loaded from `<config>/tokenizers/` (`operator/tokenizers.ts`), and none is bundled.

**Hooks** (SPEC-0022 in project_master). Scripts the server runs at points in a session. *Config:* `hooks` maps (keyed by name) at Global, a namespace, a project (config files) and an agent (`agent.<name>.hooks`, or its agent file); `capabilities.disabled.hooks` and an agent's `hooksDisabled` turn inherited ones off unless they're `locked` (`core/v1/config/fork.ts`; `hooks` is in `CAPABILITY_KEYS`). A project's copy of its namespace's config leaves out the namespace's locked hooks, which keep running from its file (`project-config.ts` `withoutLockedHooks`). *Modules* (`operator/hooks/`): `resolve.ts` (levels, overrides, offs, locks; invalid entries kept with their problems, never stopping config from loading), `hooks.ts` (the service: the resolved set cached per folder and agent against the stamps of every file it read, an agent's own hooks read from its files rather than `config.get()`, so a save applies at once; running a hook, chaining a blocking event's runs, queueing watch runs one at a time per hook and session, 20 waiting at most), `runner.ts` (a script starts by its extension with no shell, in its own process group: the deadline and the graceful stop kill everything it started, the stop coming with the last server using the runner, `hold()`; the server's credentials are left out of its environment), `protocol.ts` (stdin and the answer), `runs.ts` (the run log in `<data>/operator/hook-runs/<sessionID>.jsonl`, deleted with its session; Test runs in `tests.jsonl` and `session.deleted` runs in `deleted.jsonl`, the last 200 each), `settings.ts` (Settings → Hooks in `<config>/namespaces/hook-settings.json`), `manage.ts` and `templates.ts` (the console's writes, below). Routes under `/operator/hook/…`. *Seams:* **every tie to OpenCode's sessions is in `operator/hooks/seams.ts`** (SPEC-0022 §12.4; its header maps each event to its V1 seam and V2 counterpart): the rest never imports session code, so a move to upstream's V2 replaces that one module. It holds a built-in plugin, which `operator/plugins.ts` loads with a dynamic import (a static one would make a cycle through session code); fork plugins run before the user's, so a hook sees what the model asked for before any user plugin changes it, and with `disableDefaultPlugins` the plugin-based events don't fire (the Hooks list says so). Only the newest seams layer acts (a test process builds several). A call's agent and model come from `chat.params` (title, summary and compaction calls left out). Tool and subagent calls (`task` is `subagent.*`, the `@agent` subtask included): `tool.execute.before` runs `tool.before` / `subagent.before` (a deny throws, so the model gets "Denied by hook <name>: <reason>" as the tool's error; a changed input replaces the call's own `args` in place after a check against the tool's schema, so the permission check inside the tool sees it; MCP's resource tools can't take one); `tool.execute.after` runs `tool.after` / `subagent.after` (a changed output, and every context under "From hook <name>:" after the result; a failed run that fails closed withholds the output); both are marked on the part's `metadata.hook`. A failed tool has no plugin seam: its `tool.after` is a watch run from the bus's `message.part.updated`. A message (`chat.message`, before it's saved; a slash command's name from `command.execute.before` in the same fiber): `prompt.submitted` refuses it by throwing (the message isn't saved; `operator.hook.refused` tells the app, which takes the optimistic message out, puts the text back in the composer and shows the reason, since `prompt_async` has already answered), replaces its text (the original on the part's `metadata.hook`) or adds a synthetic text part. A request (`experimental.chat.messages.transform`; compaction's own call, which `experimental.session.compacting` marks in its fiber, is skipped): `turn.before` (once a turn, from the session's last user message; not compaction's "continue") and `step.before` (every model call); a deny throws and ends the step's assistant message with "Stopped by hook <name>: <reason>" (the clean stop of SPEC-0022 §12.3 item 1 would need an upstream edit); `turn.before` context is saved with the user message, `step.before` context is added to that one request only and kept in the run log with the step's message (`messageID`). Compaction: `compaction.before` on `experimental.session.compacting` adds to its `context` (no deny without an upstream edit); `compaction.after` on `experimental.compaction.autocontinue` sets `enabled = false` for `continue: false` or a failed run that fails closed; both runs keep the compaction's user message. `permission.asked`: the fork line in `permission/index.ts` calls `OperatorPermissionHook.decide` once a check ends in "ask" (every level, lock and approval applied), before the ask is created; the seams register the `decide` handler, composed with any other (hooks first); an allow passes once, a deny rejects with "Denied by hook <name>: <reason>" as feedback, a failed run or no answer asks the user; either answer writes a decision record (`via: "hook"`, `who: "hook <name>"`, `permission-decisions.ts` `recordHook`). Watch events, from the bus, in the event's project: `session.created`, `session.error`, `session.deleted`, `step.after` (a step-finish part; the turn and step as they were when it came, the tools from the step's tool parts as they came), `turn.after` (a session that was busy going idle; session.idle and session.status idle come once between them) and `file.edited` (which names only the file: the call is the newest running write, edit or apply_patch of that folder). *Console* (SPEC-0022 §10, §11): `manage.ts` saves a hook into the scope's config (Global, a namespace's own layer, or a project, copy-on-write; or an agent's definition through `OperatorAgents.update`, whose patch takes `hooks` and `hooksDisabled`), turns inherited ones off or on, deletes the scope's own to Trash (kind `hook`, with its script if asked; restored by the generic config branch), runs Test (a Test run in the level's folder), and reads, writes and creates scripts (from `templates.ts`) in the scope's `hooks/` folder only. The app: Capabilities → Hooks (`pages/hooks.tsx`: the list by event with its state at the scope, Runs, the hook overlay with Overview, Script, Test and Runs, the form, and Settings → Hooks as an overlay of the tab, `?hsettings=1`, as Observability keeps its settings, so no upstream Settings file changes), run lists and details (`pages/hook-runs.tsx`), the session overlay's Hooks section, the agent overlay's Hooks tab and the agent form's Hooks section (`pages/agent-hooks.tsx`), and the agent's Sys Prompt tab's Hooks block, the hooks that can add text (`pages/agent-prompt-hooks.tsx`, ADR-0002 as amended). The session views mark what hooks did (`session-views/hook-marks*.ts(x)`): under each call through the existing `partView.after` seam (calls the chat groups, read, glob, grep and list, through `partView.marks` in `ContextToolGroup`), under a user message and a compaction through the existing `afterUser` line, and `step.before` context with its step in Detailed (from the run log); the Transcript's accounting flags text under "From hook <name>:" (`call-accounting.ts` `hook`). *Residuals:* a process a hook moves out of its group (`setsid`) outlives the deadline and the stop, as does any hook when the server is killed outright; a context a before-hook adds is lost when the tool then fails (there's no seam after a failed call).

**Messaging** (SPEC-0023 in project_master; being built in phases). A session's queue has two lanes: a message for a session that is running a turn is held in its memory lane (`operator/messaging/lanes.ts`, in-process; at most 200 a session, past that the SQLite lane): a steering one is read at the session's next step (a prompt into the running session, as before), the others stay until the turn ends and then move to the session's SQLite lane (`queue_item` in `<data>/operator/queue.sqlite`, now with `lane` and `reply_to` columns), keeping their ids, priorities and times, before the idle delivery pass. A message's id (`msg_…`) is its queue item's id. Every message is in the message log (`operator/messaging/log.ts`: tables `message` and `message_step` in the same file, keyed by the source project's unique id, written in batches off the sender's path); at start, a message the log shows held in memory goes to its session's SQLite lane (`queue.ts` `recover`). **Every tie to OpenCode's sessions is in `operator/messaging/seams.ts`** (finding a message's session, the running check, delivering and steering, a turn's end), so `queue.ts` no longer imports session code and a move to upstream's V2 replaces that one module.

**Observability** (`specs/docs/feedbacks/dashboard & observability/observability_spec.md`, SPEC-0017 in project_master). A server-wide recorder, `operator/telemetry/` (the service `telemetry.ts`, registered in `operator/nodes.ts`), turns GlobalBus events into spans in its own SQLite file, `<data>/operator/telemetry.sqlite` (WAL; `store.ts`): turns, model calls (a recorded call replaces its message's row), tool calls with salted argument and result hashes (never their content), permission waits, subagents, compactions, retries, helper runs and queue items, with one summary row per session. Handlers only queue rows (`batch.ts`); a writer flushes about once a second (`writer.ts`, `derive.ts`) and announces `operator.telemetry.written {seq}`. It also tails the server log (`logs.ts`) and samples approvals, running sessions, the queue and MCP servers every 60 s, reading MCP status only in folders with activity in the last 15 minutes. On its first start it builds history from the stored sessions, recorded calls, decision records, the queue and the log's last 10 MB (`backfill.ts`, replayed through the same ingestion); it purges what is older than `eventsDays` (whole turns; kept sessions stay) every 6 hours (`retention.ts`), and keeps hourly totals for `totalsDays` (`totals.ts`), recomputed from spans for the hours that changed, plus what deleted or purged spans added (frozen first), so deleting a session never changes them. Its API is the server-wide group `operator/http/groups/telemetry.ts` (`/operator/telemetry/…`: sessions, a session's turns, a turn's spans, spans, events with the live tail's `after=<seq>`, logs, facets, metrics, Rebuild from history, storage, keeping a session), reading with `query.ts` (the shared filter, cursors that sort on the column then the id, facets without their own filter) and `metrics.ts` (the Metrics tab's series: from spans inside the detailed window, from hourly totals past it, top 5 + Other, each series with the Events filter a point opens). The page is `/operator/observability` (`packages/app/src/operator/pages/observability/`: Sessions, Events, Metrics, Logs and Alerts tabs, the session detail, the live tail, saved views, settings and export); its charts are fork components in `packages/app/src/operator/ui/charts/` on uPlot, loaded only when the Metrics tab opens. Alerts (§14): rules are JSON files in `<data>/operator/alert-rules/` (`telemetry/alert-rules.ts`; built-in rules live in `alerts.ts` and get a file only when edited, so Reset removes it), evaluated every 60 s by `telemetry/alerting.ts` (its own service, after the recorder), which keeps each rule's state and one event per firing period in the store (schema v3) and mirrors each event as an `alert` span. Deleting a user rule moves its file to Trash (kind `alert-rule` in `trash-files.ts`); the Inbox has an Alerts tab, and operator nav items can show a count (`operator/alert-badge.ts`: Observability shows firing alerts no one acknowledged); nothing is sent outside the app. Saved views (§8.5) are JSON files in `<data>/operator/telemetry-views/` (`telemetry/views.ts`, built-ins in code; files.ts is the folder store alert rules use too), deleted to Trash (kind `telemetry-view`). Observability settings (§15) are an overlay on the page (`?settings=1`), not a Settings dialog section; they write `operatorTelemetry` and `operatorRecordCalls` in the global config (`PUT /operator/telemetry/settings`, through `OperatorConfig.update`; call recording applies when projects reload). Clear telemetry moves `telemetry.sqlite` (and its WAL) to Trash as one entry (kind `telemetry`) and reopens an empty store in place (`Store.reopen`); restoring it goes through `trash.ts`'s `telemetry` branch and `OperatorRegistry.telemetry.replaceStore`, which puts the store then in use in Trash first. Export (§16) streams CSV or JSON Lines from `GET /operator/telemetry/export` (`telemetry/export.ts`, at most 100,000 rows). The Dashboard (SPEC-0018) reads the same store through `telemetry/dashboard.ts`: `GET /operator/telemetry/attention` (what needs a person now, in a fixed order, an item a firing alert covers shown once, with the sessions running now), `/tiles` (the six tiles over 24 h to 30 d with the period before, from rows inside the detailed window and hourly totals past it; context used divides by each model's window from models.dev) and `/breakdown` (agents, tools, models or projects, several groups in one request); the handler caches tiles and breakdowns for 30 s. The page is `/operator` (`packages/app/src/operator/pages/dashboard/`: the attention strip, the six tiles with their comparisons, the Activity and Spend charts on Observability's chart components (with a daily budget the Cost view of 7 to 30 days steps by day and draws the budget line; a drag zooms the whole page to a custom range), Running now, Recent sessions, Agents and Tools; `ui/server-chip.tsx` tells Reconnecting from a quiet event stream, so no upstream file changes), wider than the other operator pages (1800 px). `GET /operator/stats`, which the old Dashboard read, stays for other callers: nothing in the app reads it now, and removing it is the user's call (SPEC-0018 §15). The store is at schema v5 (one index over tool, start, kind, MCP server and status, which the tool breakdown and the tool error rate read alone); it checkpoints its write-ahead log every 10 s from the recorder rather than inside a flush (the log file is cut back to 64 MB), and refreshes SQLite's statistics (`PRAGMA optimize`) on open, 5 minutes after start and after each purge. Performance budgets (§19) are an opt-in test: `OPENCODE_TELEMETRY_PERF=1 bun run test test/operator/telemetry/perf.test.ts`. Three fork files report to it through `operator/registry.ts` `telemetry`: decision records (which now keep the request's tool ids), `generate.ts` helper runs (with a purpose) and Trash moves. It reads upstream's shapes, so check them after a merge: the v1 session events, `permission.asked`, `session.status` retry notices, the compaction user message and its `compaction_continue` follow-up (`session/compaction.ts`), the core log line format, and the `PermissionV1` error messages it tells denials by.

**Permission levels and how a line decides** (`specs/docs/feedbacks/prompt/tool_prompt_from_permission.md` §3, with the rules the user set on 2026-10-08 and 2026-10-10). `operator/permission-live.ts` builds a session's lines in levels: OpenCode (its defaults and the built-in agent's rules, as loaded, and the truncation folder allow), Global config (if the namespace inherits it), the namespace folder's config, the project's config files (read as they are now), the agent's own rules (as just written, until the project reloads) and locks, and the session's rules. `operator/permission-model.ts` decides, from the specific to the broad and **tool first**: of the lines that match a call, only those naming the tool most narrowly decide (a `read` line before a `*` line, at any level), and among them **the most specific line wins**, in any order (A is more specific than B when A's permission and pattern both fall inside B's, computed exactly over OpenCode's wildcards). Tool first is deliberate: tools read their patterns differently (a path, a command, a URL, `VERB(target)`), so a line for every tool (`* *.env deny`) can't say what it means for each, and it gives way to any line for the tool (OpenCode's own `read * allow` included); write lines per tool. A lower level's line with the same permission and pattern replaces the inherited one; a partial overlap goes to the stricter action at one level (deny, ask, allow) and to the lower level across levels; a locked line binds every level below the one that locked it, and where a lock binds a call tool first doesn't apply ("locks hold": a line at or above the lock beats it only when more specific in both tool and pattern, so a namespace's locked `* /secret/* deny` still stops OpenCode's `read * allow`); an input no line matches is denied. **This differs from upstream on purpose**, in every namespace: OpenCode checks the last rule that matches. Examples: a config `bash: {"git *": "allow", "*": "ask"}` now allows git; an agent's `bash: allow` no longer beats a config `bash rm * deny`; explore (`read: allow`) now asks for `.env` files (OpenCode's `read *.env ask` is more specific); an agent's `read: deny` keeps read listed, because OpenCode's `.env` lines still decide those files. Upstream code that still reads `agent.permission` directly (the `/merge` posture check, code mode's MCP list, the `@agent` subtask check, `debug` commands) keeps OpenCode's rule. After a merge, check that `agent/agent.ts` still builds an agent's list as defaults, the built-in agent's rules, config `permission`, the agent's own and the truncation allow (`OperatorPermissionRules.agent` splits it that way), and that `config/config.ts` still turns legacy `tools` into rules as `permission-live.ts` `configLines` does.

**The effective permission set is kept** (`operator/permission-live.ts`, `operator/file-cache.ts`). It is needed for every ask and every model request. Levels 0–4 (OpenCode to Agent) are kept per folder, agent and namespace view, with the stamps (modification and change time in nanoseconds, size, inode) of every file they came from and of every place a config file could appear: the walk from the folder up to its worktree (outside git, to the root) with each `.opencode`, Global's folder, the namespace's `.opencode`, `~/.opencode`, the environment's files, the namespace store's `settings.json`, `projects.json` and records, the marks and locks files and the agent's file. A kept entry is used only while every stamp is the same and its folder's generation is the same (it changes when the instance reloads, on `server.instance.disposed` and `global.disposed`, and when an agent's rules are written), so a change anywhere, a hand edit or a `git checkout` included, applies on the next ask. The session level (its rules and deletions) is added on top each time. Drafts are never kept, nor a subagent's levels when it inherits its parent's locks. The hot readers go through the file cache (a file is read again only when its stamp changes; parsed JSON is frozen): the layout snapshot, `projects.json`, marks, locks, session deletions and config sources; writers read their files themselves. `test/operator/permission-cache.test.ts` checks that each kind of change applies on the next ask with the cache warm and that a warm ask reads no file, and prints the timings. Measured there: an ask took about 750 ms and a model request about 490 ms before; warm, both take about 4 ms (about 130 ms cold, once per agent and folder). Most of the old cost was `OperatorPermissionRules.agent` listing every agent with its models and session counts to find one agent's file (`OperatorAgents.fileOf` now).

**Namespace and project permission levels** (tool_prompt_from_permission.md §3.2, §7). A namespace's lines are its folder's config file's `permission`, a project's its config file's (`OperatorConfig` targets), so other OpenCode clients read them; the inherited lines a level deletes and the lines it locks are kept by the fork in `<config>/namespaces/<namespace>/permissions.json` and `<config>/namespaces/project-permissions.json` (`operator/permission-marks.ts`), an agent's in the locks store (`deleted`), a session's in `<data>/operator/session-permission-deletions.json` (deleted with the session). `operator/permission-levels.ts` (`GET`/`PUT /operator/permission/level/{namespace|project}`) shows a level's lines in force, its own lines, its deletions and locks, and saves them: a line or deletion a lock above covers is refused, and so is deleting OpenCode's own lines in the OpenCode namespace (elsewhere they can be deleted; a blank slate is `* * deny` plus deleting OpenCode's lines, since OpenCode's more specific lines such as `read * allow` otherwise still decide). Agent and session saves check the same locks. The web UI edits every level with one editor (`packages/app/src/operator/ui/level-editor.tsx`): the lines a level inherits (change, delete, lock) and its own lines in the order added; the saved view lists the lines in force broadest first (`OperatorPermissionModel.order`). It is used in a project's and a namespace record's Permissions section (`ui/level-permissions.tsx`), an agent's Permissions tab and Edit form, and a session's permissions. Its user guide is `specs/docs/web_ui/permissions.md`. `permission-live.ts` reads every level's files and marks for each decision, so a save applies at once; projects reload to read the files when idle.

**Tool prompt and permissions.** The agent's Tool Prompt tab (`operator/tool-prompt.ts`) builds the tools list a request sends with the functions a request uses (`ToolRegistry.tools`, `ToolJsonSchema.fromTool`, `ProviderTransform.schema`, and R with the reachability check, as `resolveTools` now uses them), and **mirrors steps upstream does not export**: the MCP tools and MCP resource tools (`session/tools.ts`), `strict: false`, Copilot's `_noop` and the sort (`session/llm/request.ts`), `invalid` never offered (`session/llm.ts`), and the model and flag reasons a tool is not offered (`tool/registry.ts`). `test/operator/tool-prompt.test.ts` compares it with real requests; after a merge, if it fails, bring the mirror in line. The permission editor (`operator/permission-rules.ts`) labels an agent's rules by matching the parts `agent/agent.ts` puts together (defaults, the agent's definition, config `permission` and legacy `tools`, the agent's own rules, the truncation folder) and the rules `tool/task.ts` and `agent/subagent-permissions.ts` give a subagent session; `FORMS` there says which pattern each permission is asked with (from each tool's `ctx.ask` call). Check both when those files change. Session rule origins are kept in `<data>/operator/session-permissions.json`; "Always" answers and client tool switches reach it through `operator/permission-hook.ts` (the two fork lines in `permission/index.ts` and `session/prompt.ts`). **Permission requests** (fixes_spec §3, §4.3): the reply card's four choices go through `POST /operator/permission/:requestID/decide` (`operator/permission-decide.ts`): Allow (`once`), Allow for session (a session rule, origin `allow`), Allow for agent (the agent's own rule written to its file or config entry; not for built-ins) and Deny (`reject`, with the note as upstream's `CorrectedError` feedback); a rule also answers the waiting requests it covers. What is written applies at once through the hook (`operator/permission-live.ts`: the levels above, decided by `operator/permission-model.ts`; the Tool Prompt lists every level's lines with their level, origin and lock); the project reloads only when none of its sessions is running (`operator/reload-when-idle.ts`, also used by the agent Permissions editor and the Config editor instead of reloading at once). `operator/permission-decisions.ts` records every decision in `<data>/operator/permission-decisions/<sessionID>.jsonl` (deleted with the session): the fork's own (noted before it replies), upstream `permission.replied` events from other clients (the TUI, API clients; a reject's cascade and an Always's covered requests told apart by arriving in the same moment), requests whose session stopped or whose project reloaded, and the ones a merge turn withdraws (`merge/turn.ts`). It also keeps the requests waiting in every project, for the Permission Inbox. **Locks** (fixes_spec §4.2): an agent's rules its sessions may not override, by permission and pattern, kept per project and agent in `<data>/operator/agent-permission-locks.json` (`operator/permission-locks.ts`), with a subagent's choice of its own locks or its own and its parent session's agent's. They are not copied into session rule lists: a lock marks the agent level's line, and for an input a locked line matches only the agent level and above decide (permission-model.ts), so a change applies at once. Allow for session is refused for a request a lock decides, a session rule that changes a locked one is refused, and an Always answer is not kept for a locked rule. A locked `*` deny also removes the tool from the request (R's reachability check). Limits: upstream's own "always" path (the TUI) approves the session's other waiting requests without the hook, so it can get past a lock for those; a TUI "deny with note" is recorded without its note.

**Upstream's worktree race (fixed in the fork).** The HttpApi gate's effect mode used to hang on upstream's `worktree.create` scenario (`test/server/httpapi-exercise/index.ts`), about one run in four when run alone. The server answers and keeps loading the new worktree's instance in the background (`createFromInfo` forks `boot` in `src/worktree/index.ts`); the scenario removes the worktree and its runtime closes while that load is still going. `InstanceStore` runs each load in a fiber forked into its own scope (`completeLoad`), and its finalizer on that scope, `disposeAll`, waits for every load's deferred; closing the scope interrupted the load before it completed its deferred, so `disposeAll` waited forever, in a release the scenario's 30-second timeout can't interrupt. The same happened at a server shutdown during an instance load. The fork's line in `src/project/instance-store.ts` (table above) settles an interrupted load. `script/fork/upstream-merge.sh --check` still gives the gate 10 minutes and one retry; drop the retry once upstream has the fix.

**Selectable text.** Upstream makes the new layout's content area unselectable (`select-none` in `pages/layout-new.tsx`), and its settings panel too. The fork turns selection back on for text everywhere with one unlayered stylesheet, `packages/app/src/operator/ui/selectable.css` (loaded with the operator sidebar), and keeps controls unselectable; no upstream file changes. If upstream adds selection rules more specific than it, or new kinds of controls, check them against it.

**Trash.** Every delete in the operator pages moves the item to Trash (`operator/trash-files.ts` on disk, `operator/trash.ts` and `operator/trash-items.ts` as services; routes under `/operator/trash`): files and folders are moved into the data folder's `operator/trash/<id>/`; **a project is OpenCode's record of a folder, never the folder** (the user, 2026-10-12): trashing one keeps its prompt and agent settings in Trash, archives its sessions and hides it from the lists, and never moves or deletes the folder (deleting it for good removes its sessions and its database record when that record is the folder's alone: upstream gives clones of one repository the same id); config entries (MCP servers, agents and commands defined in config) are removed and kept, to be written back on restore into the file they came from: the project's, the namespace's (recorded with its id) or Global's. Deleting from Trash is for good (sessions with it). Older project entries that still hold a folder restore it as before. Upstream has no unarchive (its session projector leaves the archive time when an update has none), so restoring clears it in the session row and then publishes the update; if upstream adds unarchive, use it. The Trash page is `/operator/deleted`, since `/operator/trash` is an API route.
